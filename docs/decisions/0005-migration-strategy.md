# 5. Migration strategy: append-only revisions, tested from empty

* Status: Accepted
* Date: 2026-10-06
* Phase: 1

## Context

The schema is the contract the application and the invariants depend on. Phase 1 has to
create it deterministically on a fresh machine, prove that the migration and the
SQLAlchemy metadata agree, and allow a rollback where that is practical. The project
rule is explicit: **never modify a migration that is already part of history.**

## Decision

* **One revision per schema change, append-only.** `migrations/versions/0001_initial_schema.py`
  creates everything in Phase 1; any later change is a new revision with
  `down_revision` pointing at the current head. Editing an applied revision is forbidden:
  it silently diverges from every environment that already ran it.
* **Deterministic ordering.** Tables are created parents-first and dropped
  children-first, so neither direction can hit a foreign key violation.
* **Every revision implements `downgrade()`** and is exercised: the migration test
  upgrades, downgrades to `base`, and upgrades again on a scratch database.
* **Autogenerate, then review.** Revisions are generated with
  `alembic revision --autogenerate` and reviewed by hand; the DDL carries the named
  constraints the domain depends on (a generated name that drifts between environments
  is a bug waiting for a bad `DROP CONSTRAINT`). Autogenerated revisions must import
  `from sqlalchemy.dialects import postgresql` for `JSONB` columns.
* **Drift is a test failure.** `tests/integration/test_migrations.py` runs
  `compare_metadata` against a migrated scratch database with `compare_type=True` and
  `compare_server_default=True`, and asserts the result is empty.
* **The URL comes from settings, never from the repository.** `migrations/env.py`
  resolves `ARAD_DATABASE_URL` (or `-x db-url=…`), so a migration can never be applied
  to the wrong database because someone left a local connection string in `alembic.ini`.
* **The test database is migrated, never hand-built.** A suite that runs against a
  schema nobody can reproduce proves nothing; the migration test asserts the test
  database is at head.
* **PostgreSQL supports transactional DDL**, so a failed revision rolls back instead of
  leaving a half-applied schema. `render_as_batch` is therefore off.
* **Data migrations are separate revisions and idempotent.** Phase 1 has none, but the
  rule is recorded so the first backfill is written as its own revision with a
  `downgrade` that is honest about what cannot be undone.

## Consequences

* `docker compose up` on a clean machine produces exactly the schema the tests assert on.
* A destructive change is a two-step: add the new thing, migrate the data, then remove
  the old thing in a third revision. Slower, but reversible and reviewable.
* Migration files must be formatted manually: the alembic `[post_write_hooks]` ruff hook
  does not work (it looks for `console_scripts.ruff` on `PATH`), so it was removed rather
  than left broken.

## Runbook

```bash
ARAD_DATABASE_URL=postgresql+asyncpg://arad:arad@localhost:5432/arad alembic upgrade head
ARAD_DATABASE_URL=... alembic downgrade -1          # one step back
ARAD_DATABASE_URL=... alembic history --verbose
ARAD_DATABASE_URL=... alembic upgrade head --sql    # offline SQL, for review
```

Before applying in production: read the revision, check that `downgrade()` is honest,
and take a backup. Rollback is not a substitute for a backup.

## Alternatives considered

* **`Base.metadata.create_all()` at startup** — rejected: no history, no review, no
  rollback, and it hides destructive changes.
* **Squashing 0001 later** — not needed in Phase 1; the rule is that history is
  append-only, and a squash would invalidate every environment that already ran it.
